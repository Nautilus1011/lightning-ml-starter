# Claude Code と進める開発

[Claude Code](https://docs.claude.com/en/docs/claude-code/overview) は、ターミナルで動くコーディングエージェントです。  
ファイルを読み、コマンドを実行し、コードを書き換えるところまで自分で進めてくれます。

ただし、何も伝えずに任せると「動くけれど、このリポジトリの流儀に合わないもの」が出来上がります。  
このリポジトリでは、**守ってほしいことと作業の手順をファイルに書いて渡す**ことで、エージェントに毎回同じ品質で動いてもらう仕組みを用意しています。

このドキュメントでは、その仕組みと、使うときの考え方を説明します。
Claude Code 以外のコーディングエージェント（Codex CLI、Cursor など）でも、考え方はそのまま使えます。

---

## 全体像

```
.
├── CLAUDE.md                    # 最初に読まれる「このリポジトリの取扱説明書」
└── .claude/
    ├── settings.json            # 実行してよいコマンド・確認が必要なコマンド
    ├── rules/                   # 常に守ってほしいルール
    │   ├── github-workflow.md    #   ブランチ・コミット・PR の作法
    │   ├── coding-standards.md   #   コードの書き方、Lightning の責務分担
    │   ├── ml-research.md        #   実験・再現性のルール
    │   ├── experiment-report.md  #   実験記録（EXPERIMENT.md）の書き方
    │   └── project-guardrails.md #   絶対にやってはいけないこと
    └── skills/                  # 呼び出して使う作業手順
        ├── issue/               #   /issue       Issue を作る
        ├── pr/                  #   /pr          PR を作る
        ├── dev-check/           #   /dev-check   PR 前の動作確認
        ├── nbexec/              #   /nbexec      ノートブックを実行する
        ├── train-loop/          #   /train-loop  学習→振り返りのループを回す
        └── train-loop-status/   #   /train-loop-status  ループの進捗を見る
```

| 種類 | いつ読まれるか | 何を書くか | 人に例えると |
|---|---|---|---|
| `CLAUDE.md` | 毎回、作業の最初に | プロジェクトの概要、環境、よく使うコマンド、完了の条件 | 配属初日に渡す資料 |
| `rules/` | `CLAUDE.md` から参照されて | 常に守るべき制約。短く、言い切りで書く | 社内規程 |
| `skills/` | `/pr` のように呼んだとき、または必要だと判断したとき | 特定の作業の手順 | 作業マニュアル |
| `settings.json` | ツールを実行するたび | コマンドの許可・確認・禁止 | 権限設定 |

ポイントは**役割ごとにファイルを分けること**です。  
全部を `CLAUDE.md` に詰め込むと、長くなって大事なルールが埋もれます。いつも必要な情報は `CLAUDE.md` に、特定の作業でだけ必要な手順は `skills/` に分けておくと、エージェントは必要なときに必要な分だけ読みます。

---

## CLAUDE.md — 最初に渡す取扱説明書

新しく来たメンバーに最初に伝えることを書きます。このリポジトリでは次の構成にしています。

1. **プロジェクト概要**: 何のためのリポジトリで、誰が使うか
2. **ディレクトリの見方**: どこに何があるか
3. **開発環境と実行コマンド**: Docker の起動、学習・推論・検証のコマンド
4. **実装方針**: 迷ったときの判断基準
5. **実装完了の必須チェックリスト**: 「終わった」と言ってよい条件
6. **参照ルールとスキルの一覧**

特に効くのが 5 のチェックリストです。  
エージェントは「コードを書いた」時点で完了と考えがちです。「`compileall` が通る」「実行できなかった検証は PR に書く」「マージはしない」といった完了条件を明示しておくと、作業の終わり方がそろいます。

## rules/ — 常に守ってほしいルール

ルールは**理由を長々と書かず、守ってほしいことを言い切りで書く**のがコツです。  
エージェントが判断に迷う場面（どのブランチ名にするか、何をコミットしてよいか）を先回りして書いておきます。

このリポジトリで特に重要なルールと、それを書いた理由です。

| ルール | 理由 |
|---|---|
| `main` に直接コミットしない、PR はマージしない | 変更を必ず人がレビューしてから取り込むため |
| 実行していない検証を実施済みと書かない | エージェントは「たぶん動く」を「動いた」と書いてしまうことがある。研究では致命的 |
| `data/`・`outputs/`・重み・`.env` をコミットしない | `git add .` で巨大なファイルや API キーを入れる事故を防ぐ |
| 比較実験は差分を 1 つずつ | 一度に複数を変えると、何が効いたか分からなくなる |
| コードを変えたら `docs/` も更新する | このリポジトリは教材なので、ドキュメントとコードのずれが一番の害になる |

## skills/ — 呼び出して使う作業手順

決まった手順がある作業は、スキルにしておくと毎回同じ品質で実行されます。  
`/pr` のようにスラッシュで呼び出せるほか、エージェントが説明文を読んで必要だと判断したときにも使われます。

```text
> /issue 推論結果を CSV でも保存したい
> /dev-check
> /pr 12
```

スキルの中身は普通の Markdown です。先頭の `description` に「何をするスキルか」を書き、本文に手順・ルール・コマンドのひな形を書きます。

### よい手順書にするコツ

- **人の確認を挟む場所を決めておく**: `/issue` は作成前に本文を見せる、`/nbexec` は証跡のノートブックを差し替える前に確認する、など
- **報告の形を決めておく**: `/dev-check` は `OK:` / `SKIP:` の形式で、省略した理由も書かせる
- **このリポジトリの具体的なコマンドを書く**: `PYTHONPATH=src` や `docker compose exec dev` など、汎用の知識では出てこない部分こそ書く

### /train-loop — 学習の試行錯誤を任せる

一番大きなスキルです。人が `workspace/train-loop/BRIEF.md` に**目標と制約**を書き、その範囲内でエージェントにハイパーパラメータの試行錯誤を任せます。

```
THINK      仮説を立て、変える設定を 1 つ決める
  ↓
DRY-RUN    1 エポックだけ回して、壊れていないか確かめる
  ↓
EXECUTE    本番の学習を回す
  ↓
MONITOR    ログを見て、エラーや NaN がないか確認する
  ↓
REFLECT    結果を記録し、次の仮説につなげる → THINK に戻る
```

任せきりにしないための工夫として、次の仕組みを入れています。

| 仕組み | 役割 |
|---|---|
| `allowed_overrides` / `frozen_constraints` | 触ってよい設定と、触ってはいけない条件を人が決める |
| 停止条件 | ループ回数・時間・目標値・連続エラーのどれかで必ず止まる |
| `HUMAN_DIRECTIVE.md` | ループの途中で人が方針を差し込める |
| `LOOP_LOG.md` / `KNOWLEDGE.md` | 何を考えて何を試したかが、すべて記録に残る |

## settings.json — 権限の線引き

エージェントがコマンドを実行するたびに確認を求められると、作業が進みません。逆に、何でも自由に実行させるのは危険です。  
`settings.json` で次のように線を引いています。

| 区分 | コマンド | 考え方 |
|---|---|---|
| `allow`（確認なしで実行） | `git status`・`git diff`・`compileall` など | 読むだけ、または何も壊さない |
| `ask`（実行前に確認） | `git push --force`・`git reset --hard`・`gh pr merge` など | 取り消しにくい操作 |
| `deny`（禁止） | `.env` の読み取り | API キーをエージェントに渡さない |

個人的に許可を足したい場合は `.claude/settings.local.json` に書きます（Git 管理外）。

## 開発の流れ

このリポジトリでの、エージェントと一緒に進める標準的な流れです。

```
1. /issue でやることを Issue にする
2. 方針をエージェントと相談する（いきなり書かせない）
3. ブランチを切って実装してもらう
4. /dev-check で動作確認する
5. /pr で PR を作ってもらう
6. 人が差分を読んでレビューし、マージする
```

---

## 使うときの心がけ

- **最初に方針を相談する**: いきなり「実装して」ではなく「どう直すか案を出して」から始めると、手戻りが減ります
- **小さく頼む**: 1 回の依頼は 1 つの目的に絞ります。PR も小さいほうがレビューしやすくなります
- **差分は必ず自分で読む**: エージェントが書いたコードの責任は、マージした人にあります
- **「動いた」は確かめる**: 報告に `OK` とあっても、学習のような重い処理は省略されていないか確認します
- **繰り返し指摘したことはルールにする**: 同じ注意を 2 回したら、`rules/` か `CLAUDE.md` に書き足すタイミングです。設定ファイルは一度書いて終わりではなく、使いながら育てるものです

---

## 自分のリポジトリに取り入れるには

1. `CLAUDE.md` をコピーし、プロジェクト概要・コマンド・チェックリストを自分のプロジェクトに書き換える
2. `rules/project-guardrails.md` に、そのプロジェクトで絶対に避けたいことを書く
3. `rules/` と `skills/` から使えそうなものを持っていき、コマンドやパスを合わせる
4. 使いながら、エージェントがつまずいたところをルールに足していく

Claude Code 自体の機能の詳細は、[公式ドキュメント](https://docs.claude.com/en/docs/claude-code/overview)を参照してください。
